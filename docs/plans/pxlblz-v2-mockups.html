Cards are alive

Each card runs the real preview engine at reduced pixel count, staggered and paused off-viewport. The launch-post lesson was "lead with motion" — this page is the motion.

Real URLs at last

v2 introduces routing. /gallery is the signed-out landing; each pattern gets /p/<slug> — the shareable link for Show-and-Tell posts.

Familiar vocabulary, new frame

The dimension lens (All/1D/2D/3D) and section names carry over from the v1 rail — same filters, now applied to a grid instead of a sidebar list.

Two doors out

"Open Studio →" is the only bright accent in the top bar. Signed-in users land in the Studio directly; the Gallery remains reachable from the Studio's catalog entry point.

Pattern detail — a big preview, the pattern's own controls, no Monaco

Clicking a card gives the pattern the whole stage. Controls are the pattern's real exported sliders. Source is one click away, but reading code is opt-in here — this view is for the pattern consumer.

Consumer-first, author-optional

The v1 retro's conclusion: the broad audience consumes patterns, it doesn't write them. Controls and Send to Controller work right here; "View source" and "Open in Studio" are the on-ramps for the authoring minority.

Send without Studio

A hardware builder can push a gallery pattern to their device without ever entering the editor — the Controller connect surface is available from this page too.

Settings that follow you in

Slider tweaks made here ride along through "Open in Studio" — the same settings-cascade layer that demo overrides use today.

Studio — the five-entity rail

The two-list rail becomes an activity strip + list pane. Your entities — Patterns, Maps, Mixins, Controllers, Shows — are the top-level nav; built-ins recede into a catalog you pull from, instead of a permanent sibling list.

Activity strip scales to five

A Patterns/Maps segmented toggle can't hold five entity kinds. The 46px strip (VS Code-style) does, keeps every kind one click away, and leaves the list pane's width for names. Labels under icons — no icon-only guessing.

Built-ins recede

No permanent "Built-in Patterns" tree. Your saved list is the rail; the catalog is the bottom strip entry and the dashed hint card when a list is short. Cloning from the catalog is the same fork flow as today.

Editor and preview unchanged

Monaco, the deck, the settings cascade, Run/Save, the controller pills — all carried over as-is. The rework is the rail and routing, not the editing core.

Implementation note

Today's rail is one 1,177-line PatternList.tsx with a two-value railMode. The strip generalizes it into one list component per entity kind behind a shared shell — a prerequisite issue in the nav-rework track.

Controller — hardware profile as a first-class entity

A Controller is no longer just a connection pill. It's a durable D1-backed entity: the physical box's inputs, its global transforms, and its per-pattern bindings — the concepts from the hardware-injection manifest, given a page instead of a YAML file.

Manifest concepts, D1 home

The PRD's manifest vocabulary survives intact — inputs, roles, smoothing/fallback, global transforms, per-pattern bindings — but lives as a cloud entity, not a workspace file. It exists and is editable even while the device is offline.

ADC1 validation built in

Pin pickers only offer WiFi-safe ADC1 pins per board variant, with the constraint explained inline — the spike finding becomes UI, not documentation trivia.

Mixins are the visible mechanics

Every transform and binding names the mixin that implements it, linking to its readable source. Nothing is generated from a hidden template — same philosophy as stock maps.

Native brightness stays the cap

The live Device card shows the device's own brightness cap in amber — injected hardware brightness only dims inside it, never exceeds it.

Mixin — readable code, bound elsewhere

A mixin is a visible chunk of Pixelblaze-dialect source that the pass engine injects around a pattern at push time. Built-ins ship read-only and cloneable, exactly like stock maps; parameters are bound where the mixin is used (on a Controller or Show), never inside the mixin itself.

No magic, like maps

The stock-maps promise — "here's the actual code" — extends to hardware wiring. What the pass engine injects is this file, verbatim, with @param slots filled from the binding. Cloning it makes a personal variant, same as cloning a stock map.

The pass taxonomy shows up as badges

inject / intercept / bind chips on the rail teach the vocabulary passively. Intercept mixins (brightness, power cap) also rewrite call sites — that part can't be plain visible code, so the transform summary reports it.

Right pane repurposed

A mixin has no preview to render, so the preview pane becomes provenance: where the mixin is used, and the last transform summary with a path to the generated artifact — the inspection affordance the PRD requires.

Show editor — clips, transitions, zones (sketch)

Lower fidelity, on purpose — this ships after the pass engine proves out. A Show treats whole patterns as clips on zone tracks, compiles to a single generated Pixelblaze pattern, and reports its device budget honestly.

Zones are semantic, not electrical

Tracks are named zones (arch-left, rock-wash); the zone→pixel mapping lives on the target Controller. The same show retargets to different hardware by remapping zones, per the orchestration doc's creative/deployment split.

Adaptations live on the clip

Palette swap, mirror, phase, brightness envelope attach to the pattern-in-this-show — the original pattern is never forked. This is the "adaptation on the relationship" decision: no standalone recipe entity.

The budget bar is load-bearing

A show compiles to one generated pattern; the device's code-size and FPS ceilings are real. The compile bar surfaces artifact size against the measured device budget and confirms time-sliced emission — the honesty the cost model exists for.

Everything inspectable

"View generated pattern" opens the compiled artifact read-only — a Show is ultimately just a Pixelblaze pattern you could paste anywhere, keeping the no-magic promise.

Deliberately single-theme: these mock a dark-only IDE, so the review page commits to the same ground. Fonts fall back from IBM Plex Mono / Geist to system equivalents where not installed — proportions are set to survive the swap. Previews are lightweight canvas sketches, not the real fixed-point engine.
