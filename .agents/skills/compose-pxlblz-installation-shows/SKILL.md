# Compose PXLBLZ Installation Shows

Translate a compelling, performance-aware visual plan into a scored physical instrument. Preserve the protected premise and visual grammar while adding topology, routing, shared state, transition policy, long-form composition, and production proof.

## Establish the three inputs

1. Use `design-compelling-pxlblz-visuals` to produce the Visual Direction Packet. If the user supplied an equivalent brief, normalize it to that contract. Do not reinvent the aesthetic doctrine here.
2. Use `co-design-pxlblz-visual-performance` to produce the Visual Performance Plan. Treat its identity, evaluation, transition, memory, artifact, and fallback decisions as implementation constraints to prove, not suggestions to check at the end.
3. Write the Stage Contract: dimensionality, physical silhouettes, pixel counts, index ranges, spatial relationships, viewing direction, Controller profile, and whether the piece is exploratory or bound to real hardware.

Read [performance-cost-ladder.md](references/performance-cost-ladder.md) before choosing Show structure. Read [pxlblz-show-model.md](references/pxlblz-show-model.md) before changing a PXLBLZ repository or compiling a Show.

## Turn the Stage into instruments

1. Inventory every physical surface and assign a perceptual role: hero, family member, countervoice, punctuation, frame, or void.
2. Prefer 2D when frontal graphic impact is the point. Add 3D only when depth changes routing, occlusion, motion, or the viewer's reading.
3. Translate the packet's visual voices onto physical instruments. Preserve a clear hero and make repeated surfaces behave as a family.
4. Reuse one Pattern instance and clock across repeated surfaces and Scenes when their state can agree. Derive difference through affine Effects, mirroring, phase, address changes, masks, properties, staggered scheduling, and local physical dimensions.
5. Create a unique Pattern instance only when independent private state, controls, or clock creates a visible requirement. Do not assign unique instance IDs merely to distinguish Scene records, force routine restarts, or make generated content look organized.
6. Map the packet's section arc onto Scenes and scene-local placement schedules. Use Cuts when the visual law changes hard; buy blends or motion only when the boundary itself is an important visual event.
7. Keep topology separable from modeled resolution so the same score can downscale without changing its physical logic.

## Preserve the performance plan while composing

Use the cheapest Show structure that keeps the protected visual purchase intact.

- Build a small cast of reusable Pattern voices. Prefer repetition with legible variation over many nearly identical unique sources.
- Keep steady-state and peak renderer evaluation within the plan. A long Show may compile many branches while running only a few, so track active work and static artifact size separately.
- Treat each Scene stack, transition boundary, routing specialization, and generated wrapper as potential artifact growth. Measure one instance, repeated-identical instances, and varied instances before authoring the full score.
- For a transition or teaching catalogue, spend the budget on the concept being demonstrated. Reuse neutral content identities unless independent content state is itself the lesson.
- Precompute frame-wide phrase, palette, mode, density, and clock values outside per-pixel renderers. Branch on coarse physical identity before detailed work.
- Apply the Visual Performance Plan's fallback order when a budget tightens. Preserve the hero, reduce supporting texture and transition luxury first, and document any changed premise.

## Implement in PXLBLZ

Follow the repository's issue, TDD, documentation, and browser-verification workflows.

1. Add the Stage as Mapper-compatible source. Keep Pattern `sample` coordinates distinct from preview `pos` geometry.
2. Write failing tests for point count, index groups, topology, and aspect before cataloguing the map.
3. Add bespoke raw Patterns or use Patterns proven through `build-efficient-pxlblz-patterns`. Smoke-test compilation, controls, lit output, and planned cost limits.
4. Compile one representative Scene and transition. Record the three performance ledgers before extending the score.
5. Add the Installation Show with an exact fixed output contract, complete non-overlapping ranges, explicit composition, section-length Scenes, and production compilation coverage.
6. Re-run the same-versus-varied scaling probe at a representative section and then at full duration. Unexpected linear growth is a design or compiler finding, not merely a number to accept.
7. Assert shared Pattern identity where intended, evaluation formula, duration, palette events, representative frame differences, routing coverage, transition policies, and visual-direction invariants.
8. Open the built-in Show in the production editor. Inspect ordinary frames as well as accents. Capture establishment, subtraction or intruder, transition, and peak. Compare them against both input plans.
9. Qualify production artifact bytes, VM words, render-target reservations, peak evaluations, and hardware frame metrics. Document limitations and issue state.

## Apply the installation review

Use the companion aesthetic skill for visual judgment, then reject the installation when any answer is weak:

- Can a viewer identify each physical instrument and its role in one second?
- Does the hero remain dominant after routing and transforms?
- Do repeated surfaces share identity and clock while performing visibly different roles?
- Does every independent Pattern instance create visibly necessary independent behavior?
- Does every Scene change the system rather than merely shuffle texture?
- Do transition costs match their visual importance?
- Are active render cost, static artifact growth, and memory headroom all within their separate budgets?
- Can resolution be lowered without rewriting topology or score?
- Does the production compiler and Stage preview, rather than a side prototype, prove the result?

Finish with the compiled Show, representative captures, test commands and outcomes, cost disclosure across all three ledgers, deviations from the Visual Performance Plan, and issue state. A strong visual packet without production-path performance proof is not a finished Installation Show.
